# Data Contracts

Single source of truth for the data this platform produces and consumes.
Change this file first, then the code.

## Conventions

- Timestamps: UTC, ISO 8601, field names end in `_ts` (events) or `_at` (batch).
- Money: integer minor units (cents), plus a `currency` code. Never floats.
- IDs: strings (UUIDs), generated by the simulator.
- Every event has a unique `event_id`, used later for deduplication.

## Behavior assumptions

These numbers drive the simulator. They only need to be realistic and written down.

**Population and scale**
- About 50 campaigns, roughly 40 active at any time; each runs 14 to 60 days.
- 5,000 donors at the start, plus about 200 new users per day.
- Platform split: 60% Android, 40% iOS.
- Countries: mostly UAE and Egypt, with a few others.

**Sessions and funnel**
- 1 to 3 sessions per active user per day, with an evening peak.
- Campaign views per session: average 5, range 1 to 12.
- View source: 50% home recommendation, 30% search, 20% push notification.
- About 10% of views lead to `donation_started`.
- Of started donations: 70% complete (payment succeeds), 25% are abandoned (no payment record), 5% have a failed payment (a `payments` row with status `failed`, and no `donation_completed` event).

**Popularity and amounts**
- Campaign popularity is skewed: the top 10% of campaigns receive about 60% of views.
- Currency is mostly AED, some USD. Donation amounts are right-skewed: median about 50 AED, range 10 to 1,000, stored in minor units.

**Time**
- `event_ts` is the device time and should arrive in roughly increasing order per user. Late and duplicate events are injected on purpose later (Day 16).

## Key decisions

- **Why `user_id` is the Kafka partition key:** Kafka only guarantees ordering within a partition. Keying by `user_id` sends all of one user's events to the same partition, so a consumer sees each user's `app_open`, views and donation in order, while load still spreads across partitions because there are many users.
- **Why money is stored as integer minor units:** floating-point numbers can't represent most decimal values exactly (0.1 + 0.2 is not 0.3), so rounding errors creep into sums. Integers in cents add up exactly, and the `currency` field says what the integer means.
- **Why every event carries a unique `event_id`:** Kafka delivery is at-least-once in many setups, so duplicates can happen. A unique ID lets downstream models deduplicate events and makes reprocessing safe (idempotent).
